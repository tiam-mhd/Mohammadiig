# بخش اول: امنیت و احراز هویت

## ۱. حذف مقادیر پیش‌فرض خطرناک

در Backend موارد زیر نباید در محیط Production مقدار پیش‌فرض ناامن داشته باشند:

* `JWT_SECRET`
* `ADMIN_PASSWORD`
* `ADMIN_EMAIL`
* تنظیمات پیامک
* اطلاعات دیتابیس
* تنظیمات CORS

رفتار مطلوب:

* اگر `NODE_ENV=production` است و `JWT_SECRET` تنظیم نشده، برنامه اجرا نشود.
* اگر `ADMIN_PASSWORD` تنظیم نشده، برنامه اجرا نشود.
* رمز مدیر هرگز در Log چاپ نشود.
* مقدارهای پیش‌فرض فقط در محیط development مجاز باشند.
* مستندات `.env.example` کامل و فارسی‌سازی‌شده باشند.
* پس از اصلاح، یک چک امنیتی برای Environment Variables اضافه کن.

## ۲. امن‌سازی Token

در حال حاضر Access Token در سمت کلاینت Persist می‌شود.

این روند را اصلاح کن:

* Access Token در `localStorage` یا Zustand Persist ذخیره نشود.
* احراز هویت به Cookie امن و `HttpOnly` منتقل شود.
* Cookie در Production دارای `Secure` باشد.
* `SameSite` مناسب تنظیم شود.
* مسیرهای `/admin` و `/account` فقط با Session معتبر قابل دسترسی باشند.
* Logout باید Session سمت سرور یا Refresh Token را باطل کند.
* Token بعد از Logout قابل استفاده نباشد.
* منطق فعلی احراز هویت مشتری و مدیر حفظ شود.

## ۳. محافظت واقعی پنل مدیریت

محافظت پنل مدیریت فقط به Client Component وابسته نباشد.

پیاده‌سازی کن:

* Middleware یا Server-side Guard برای `/admin`
* بررسی معتبر بودن Session
* بررسی `role=admin`
* جلوگیری از نمایش محتوای پنل قبل از بررسی دسترسی
* هدایت صحیح کاربر غیرمجاز به صفحه ورود فارسی
* عدم افشای اطلاعات پنل در HTML اولیه برای کاربر غیرمجاز

## ۴. تکمیل OTP

جریان OTP را بررسی و اصلاح کن:

* محدودیت ارسال بر اساس شماره موبایل و IP
* محدودیت تعداد تلاش برای هر Challenge
* انقضای قطعی Challenge
* غیرقابل استفاده بودن Challenge مصرف‌شده
* جلوگیری از Race Condition
* جلوگیری از ارسال چند OTP همزمان
* حذف یا Mask کردن `debugCode` در Production
* عدم نمایش جزئیات حساس در Error Response
* پاک‌سازی OTPهای منقضی‌شده
* پیام‌های کاملاً فارسی
* تست کامل Login، Register، Forgot Password و Change Mobile

# بخش دوم: اصلاح جریان پیش‌فاکتور، سفارش و فاکتور

## ۵. تراکنشی کردن تبدیل پیش‌فاکتور به سفارش

در تبدیل Quotation به Order، ایجاد موارد زیر باید در یک تراکنش دیتابیس انجام شود:

* Order
* Order Items
* Invoice
* تغییر وضعیت Quotation در صورت نیاز

اگر هر مرحله شکست خورد، همهٔ عملیات Rollback شوند.

همچنین:

* تبدیل تکراری یک پیش‌فاکتور نباید سفارش جدید بسازد.
* برای `referenceQuotationId` محدودیت یکتا ایجاد کن.
* شماره سفارش باید یکتا باشد.
* شماره فاکتور باید یکتا باشد.
* Race Condition بین دو درخواست همزمان کنترل شود.
* در صورت وجود سفارش قبلی، همان سفارش برگردانده شود.
* خطاها برای کاربر فارسی باشند.

## ۶. اعتبارسنجی وضعیت‌ها

تمام وضعیت‌های سفارش، پیش‌فاکتور، فاکتور و پرداخت را به Enum معتبر تبدیل کن.

از دریافت `string` آزاد جلوگیری کن.

وضعیت‌های مجاز باید در Backend و Frontend یکسان باشند.

برای هر تغییر وضعیت:

* وضعیت قبلی بررسی شود.
* انتقال‌های غیرمجاز مسدود شوند.
* تغییر وضعیت در Audit Log ثبت شود.
* پیام خطا فارسی باشد.

نمونه وضعیت سفارش:

```text
pending
confirmed
processing
ready_for_delivery
delivered
cancelled
```

نمونه وضعیت پیش‌فاکتور:

```text
draft
sent
accepted
rejected
expired
```

## ۷. کنترل اعتبار پیش‌فاکتور

هنگام پذیرش پیش‌فاکتور:

* تاریخ اعتبار بررسی شود.

* پذیرش در Audit Log ثبت شود.
* تاریخ و کاربر پذیرنده ذخیره شود.

## ۸. اصلاح فاکتور

فاکتور باید:

* شماره یکتا داشته باشد.
* وضعیت معتبر داشته باشد.

# بخش سوم: اصلاح سیستم پرداخت

## ۹. جلوگیری از پرداخت تکراری

در ثبت پرداخت:

* مبلغ صفر یا منفی پذیرفته نشود.
* مبلغ بیشتر از مانده فاکتور پذیرفته نشود.
* مبلغ کل پرداخت‌شده از مبلغ فاکتور بیشتر نشود.
* برای هر فاکتور پرداخت Pending تکراری ساخته نشود.
* `transactionId` در صورت وجود Unique باشد.
* مالکیت فاکتور حتماً بررسی شود.
* مشتری نتواند فاکتور مشتری دیگر را پرداخت کند.
* پرداخت باید داخل Transaction ایجاد شود.

## ۱۰. هماهنگ‌سازی وضعیت Payment، Invoice و Order

هنگام تغییر وضعیت پرداخت:

* اگر پرداخت تأیید شد:

  * Payment به `completed`
  * Invoice به `paid` یا `partially_paid`
  * Order به وضعیت پرداخت متناظر
* اگر پرداخت رد شد:

  * Payment به `failed`
  * Invoice به وضعیت مناسب
* اگر پرداخت لغو شد:

  * Payment به `cancelled`
* مجموع پرداخت‌ها مجدداً از دیتابیس محاسبه شود.
* مبلغ پرداخت‌شده از Frontend پذیرفته نشود و Backend مرجع نهایی باشد.
* کاربر تأییدکننده در `processedBy` ذخیره شود.
* زمان تأیید ذخیره شود.
* همهٔ تغییرات در Audit Log ثبت شوند.

## ۱۱. اصلاح صفحه حساب مشتری

در پنل مشتری:

* پس از ثبت پرداخت، اطلاعات با API مجدداً Sync شود.
* دکمه ثبت پرداخت تا مشخص شدن نتیجه غیرفعال باشد.
* پرداخت‌های تکراری نمایش داده نشوند.
* وضعیت پرداخت با برچسب فارسی نمایش داده شود.
* خطاهای پرداخت فارسی باشند.
* وضعیت Pending، Completed، Failed و Cancelled از هم تفکیک شوند.
* در صورت پرداخت موفق، فاکتور و سفارش به‌روزرسانی شوند.

* OrdersService

* CustomersService

سناریوهای ضروری:

* ورود مشتری
* ورود مدیر
* دسترسی نقش‌های مختلف
* درخواست پیش‌فاکتور
* پذیرش پیش‌فاکتور منقضی
* تبدیل تکراری پیش‌فاکتور
* Rollback تراکنش سفارش
* پرداخت تکراری
* پرداخت بیشتر از مبلغ فاکتور
* تأیید و رد پرداخت
* دسترسی مشتری به فاکتور مشتری دیگر
* Upload فایل غیرمجاز
* Restore فایل آلوده یا خراب
* Pagination

## ۲۴. تست E2E

حداقل یک جریان کامل E2E ایجاد کن:

```text
ثبت‌نام مشتری
→ ورود با OTP
→ مشاهده محصول
→ ثبت درخواست قیمت
→ مشاهده توسط مدیر
→ تغییر وضعیت به sent
→ پذیرش توسط مشتری
→ تبدیل به سفارش
→ ایجاد فاکتور
→ ثبت پرداخت
→ تأیید پرداخت توسط مدیر
→ به‌روزرسانی وضعیت سفارش
```

# بخش دوازدهم: کیفیت کد و آماده‌سازی Production

## ۲۵. اضافه کردن Pipeline

در GitHub Actions این مراحل را اضافه کن:

1. نصب وابستگی‌ها
2. بررسی Lock File
3. ESLint
4. TypeScript Check
5. Unit Tests
6. Integration Tests
7. Build Backend
8. Build Frontend
9. اجرای Migration روی دیتابیس تست
10. بررسی امنیت Dependencyها

Build نباید با Warningهای جدی یا Error تمام شود.

## ۲۶. بررسی کیفیت نهایی

قبل از پایان کار:

* `npm run build` ریشه اجرا شود.
* Build بک‌اند موفق باشد.
* Build فرانت‌اند موفق باشد.
* تمام تست‌ها اجرا شوند.
* Migrationها از ابتدا روی دیتابیس خالی اجرا شوند.
* Migrationها روی دیتابیس موجود نیز بدون از دست رفتن داده اجرا شوند.
* هیچ Secret در Repository نباشد.
* هیچ دادهٔ آزمایشی در Production باقی نماند.
* هیچ متن انگلیسی قابل مشاهده برای کاربر باقی نماند، مگر نام برند یا مقدار فنی ضروری.
* RTL همهٔ صفحات بررسی شود.
* Console Error و Unhandled Promise بررسی شود.
* APIهای محافظت‌شده بدون Token قابل استفاده نباشند.
* APIهای مدیریتی با نقش customer قابل استفاده نباشند.

# خروجی‌های اجباری

در پایان کار این موارد را ارائه کن:

1. خلاصهٔ تغییرات انجام‌شده
2. فهرست فایل‌های تغییرکرده
3. فهرست Migrationهای جدید
4. فهرست Endpointهای جدید یا تغییرکرده
5. فهرست تست‌های اضافه‌شده
6. نتیجهٔ اجرای Build
7. نتیجهٔ اجرای Test
8. مشکلات باقی‌مانده، در صورت وجود
9. دستور اجرای Local
10. دستور اجرای Migration
11. متغیرهای Environment جدید یا تغییرکرده
12. راهنمای Deploy Production
13. گزارش اینکه تمام متن‌های قابل مشاهده برای کاربر فارسی هستند

در طول پیاده‌سازی، هر مرحله را واقعاً اجرا و Verify کن. فقط توضیح یا پیشنهاد ارائه نده؛ تغییرات را در کد اعمال کن.

تا زمانی که Build، Test و جریان کامل خرید و پرداخت با موفقیت بررسی نشده‌اند، کار را تمام‌شده اعلام نکن.
