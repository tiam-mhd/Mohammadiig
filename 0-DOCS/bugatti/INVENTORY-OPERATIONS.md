# راهنمای عملیات انبار

## دامنهٔ موجودی

موجودی فیزیکی فقط برای دو نوع قلم ثبت می‌شود:

- گونهٔ محصول در جدول product_variants
- قطعهٔ یدکی در جدول spare_parts

محصول والد، خدمت، مشخصات محصول، مرجع قیمت و سفارش تولید موجودی مستقل ندارند. فروش قطعهٔ یدکی از انبار مرکزی انجام می‌شود؛ مکان کارخانه از طریق انتقال انبار تأمین یا تخلیه می‌شود.

## مانده و دفتر گردش

جدول inventory_stock_levels ماندهٔ هر قلم را برای هر مکان نگه می‌دارد:

- on_hand: تعداد فیزیکی
- reserved: تعداد نگه‌داشته‌شده برای سفارش‌های باز
- قابل‌استفاده: on_hand منهای reserved

هر تغییر فیزیکی یک ردیف در inventory_movements می‌سازد. این دفتر در پایگاه‌داده فقط درج‌پذیر است؛ اصلاح یا حذف رویداد به‌جای بازنویسی سابقه باید با رویداد جبرانی انجام شود. اصلاح شمارش، مقدار قبل و بعد، کاربر و علت را ذخیره می‌کند.

## مهاجرت و دادهٔ قدیمی

مهاجرت 1710000041000-inventory-locations-and-ledger مکان‌های «انبار» و «کارخانه» را می‌سازد. مقدار قدیمی stock_quantity گونه‌ها و قطعات را به‌عنوان ماندهٔ آغازین انبار مرکزی ثبت می‌کند؛ ماندهٔ کارخانه از صفر آغاز می‌شود. برای هر مقدار مثبت، یک رویداد opening_balance ساخته می‌شود.

ستون‌های legacy برای سازگاری و تطبیق باقی می‌مانند، اما مسیر عملیاتی موجودی نباید آن‌ها را تغییر دهد یا از آن‌ها برای تصمیم فروش استفاده کند. ماندهٔ جاری از دفتر و جدول‌های inventory_stock_levels خوانده می‌شود.

این مهاجرت در صورت وجود رویداد موجودی rollback نمی‌شود؛ پیش از هر اقدام عملیاتی روی طرح پایگاه‌داده، از داده‌ها نسخهٔ پشتیبان بگیرید و دفتر را تطبیق دهید.

## انتقال بین انبار و کارخانه

1. کاربر پیش‌نویس را با مبدأ، مقصد، یادداشت و اقلام می‌سازد یا ویرایش می‌کند.
2. ساخت و ویرایش پیش‌نویس مانده را عوض نمی‌کند.
3. ثبت نهایی، در یک تراکنش مبدأ را کم، مقصد را زیاد، وضعیت را نهایی و دو رویداد transfer_out و transfer_in را ثبت می‌کند.
4. اگر مبدأ موجودی قابل‌استفادهٔ کافی نداشته باشد، کل تراکنش rollback می‌شود.
5. ثبت دوبارهٔ همان انتقال، رویداد تازه‌ای نمی‌سازد. لغو فقط برای پیش‌نویس است.
6. برگشت انتقال نهایی با انتقال جبرانی در مسیر معکوس ثبت می‌شود؛ رویداد اصلی باقی می‌ماند.

## فروش، رزرو و مرجوعی

- checkout قطعات، تعداد را در reserved نگه می‌دارد و تعداد فیزیکی را کم نمی‌کند.
- لغو سفارش، رزرو فعال را آزاد می‌کند.
- صدور فاکتور قطعی، رزرو سفارش را مصرف می‌کند و رویداد خروج فیزیکی sale_out می‌سازد.
- پیش‌فاکتور به‌تنهایی مانده را تغییر نمی‌دهد؛ تبدیل آن به فاکتور قطعی موجودی را ثبت می‌کند.
- فاکتور حضوریِ قطعی، موجودی را هم‌زمان با ثبت فروش کم می‌کند.
- در جزئیات فاکتور، «برگشت قطعات به انبار» همهٔ قطعات همان فاکتور را یک‌بار به موجودی انبار بازمی‌گرداند. برگشت، وضعیت مالی یا مبلغ فاکتور را تغییر نمی‌دهد.

## دسترسی‌های مدیریت

API و صفحهٔ /admin/inventory از دسترسی‌های سیستمی زیر استفاده می‌کنند:

| مجوز | عملیات |
| --- | --- |
| inventory.read | مشاهدهٔ مکان‌ها، مانده‌ها، انتقال‌ها و دفتر گردش |
| inventory.create | ساخت پیش‌نویس انتقال |
| inventory.update | ویرایش پیش‌نویس |
| inventory.post | ثبت نهایی انتقال |
| inventory.cancel | لغو پیش‌نویس |
| inventory.reverse | برگشت انتقال یا قطعات فاکتور |
| inventory.adjust | اصلاح شمارش با علت الزامی |

مسیرهای HTTP زیر با احراز هویت ادمین و مجوز متناظر محافظت شده‌اند:

- GET /inventory/locations، /inventory/summary، /inventory/stock، /inventory/transfers، /inventory/movements
- POST /inventory/transfers، PATCH /inventory/transfers/:id
- POST /inventory/transfers/:id/post، /cancel، /reverse
- POST /inventory/stock/:inventoryItemId/adjustments
- POST /inventory/invoices/:invoiceId/return

شناسهٔ کاربر عامل از نشست تأییدشده گرفته می‌شود؛ کلاینت نمی‌تواند آن را در بدنهٔ درخواست تعیین کند.
