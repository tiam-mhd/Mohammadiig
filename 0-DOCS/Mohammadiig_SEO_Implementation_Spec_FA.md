# مشخصات فنی اصلاح و شروع سئوی سایت گروه صنعتی محمدی

**نسخه:** ۱.۰
**تاریخ مبنا:** ۱۰ نوامبر ۲۰۲۶
**سایت:** https://www.mohammadiig.ir
**هدف سند:** تبدیل ممیزی عمومی سئو به فهرست تغییرات فنی قابل اجرا و قابل بازبینی در مخزن پروژه.

## ۱. هدف و حدود بررسی

این سند بر اساس مشاهده‌ی عمومی سایت، پاسخ صفحه‌ها، HTML اولیه، metadata، robots.txt، sitemap.xml و محتوای قابل مشاهده در مرورگر تنظیم شده است. به Google Search Console، ابزار آمار بازدید، گزارش بک‌لینک، تنظیمات CDN/DNS یا اطلاعات تأییدشده‌ی فنی محصولات دسترسی وجود نداشت.

هدف این مرحله، برطرف کردن ایرادهای سئوی فنی و درون‌صفحه‌ای با حفظ کامل ظاهر و رفتار فعلی سایت است. این سند مجوز تغییر طراحی، منطق فروش، داده‌های واقعی شرکت یا انتشار سایت نیست.

این موارد گزارش وضعیت عمومی زمان ممیزی هستند؛ قبل از تغییر، Codex باید آن‌ها را در مخزن فعلی دوباره بررسی کند و نسخه‌ی موجود کد را مرجع نهایی پیاده‌سازی بداند.

## ۳. مرزهای غیرقابل مذاکره

موارد زیر باید بدون تغییر بمانند:

- طراحی UI، ترکیب‌بندی، رنگ‌ها، فونت‌ها، فاصله‌ها، responsive behavior، انیمیشن‌ها و transitionها.
- صفحات یا حالت‌های Loading، splash، skeleton، spinner و متن و زمان‌بندی بصری آن‌ها؛ آن‌ها را حذف، پنهان، بازطراحی یا جابه‌جا نکن.
- ناوبری، مسیر URLهای فعلی، فرم‌ها، اعتبارسنجی، سبد خرید، استعلام قیمت، احراز هویت، پنل مشتریان و رفتار موبایل.
- منطق تجاری، API contractها، نام فیلدهای ذخیره‌شده، مدل‌های دیتابیس، state management، cache policy و روش فعلی ثبت سفارش.
- داده‌های واقعی محصولات، قیمت‌ها، ظرفیت، وزن، ابعاد، متریال، گارانتی، استانداردها و ادعاهای سابقه؛ چیزی را حدس نزن یا جعل نکن.
- dependencyهای پروژه و معماری فریم‌ورک؛ برای کار سئو package جدید اضافه نکن، مگر واقعاً ضروری باشد و دلیل آن در گزارش بیاید.
- هیچ تغییر یا انتشار روی سایت production، DNS، CDN، secrets، متغیرهای محیطی، حساب‌های Search Console یا Analytics انجام نشود.

تغییرات غیرنمایشی مجاز شامل metadata، canonical، robots metadata، sitemap، JSON-LD، OG metadata، alt تصویرهای معنادار و اصلاح معنایی headingها است. اگر اصلاح SSR/SSG لازم شد، HTML اولیه را crawlable کن و با همان داده‌ی منبع و منطق فعلی hydrate کن. اجزای loading فعلی را نگه دار و فقط منبع داده‌ی اولیه را به شکل غیرنمایشی بهبود بده. محتوای موازی و پنهان مخصوص ربات نساز.

اگر هر اصلاح فنی بدون تغییر قابل مشاهده در UI یا بدون ریسک برای منطق فعلی ممکن نیست، آن بخش را متوقف کن، مورد را دقیق توضیح بده و راهکار کم‌ریسک ارائه کن.

## ۴. هدف تجاری و نگاشت موضوع به صفحه

گروه صنعتی محمدی تولیدکننده‌ی تخصصی ماشین کوبنده‌ی شهربازی است و طبق معرفی کسب‌وکار، طراحی، تجهیز، اجرا، قطعات، پشتیبانی و بخشی از سرمایه‌گذاری و بهره‌برداری مراکز تفریحی را نیز انجام می‌دهد. برند فانتینو باید فقط در جایی معرفی شود که نقش واقعی و قابل اثبات آن مرتبط باشد. هویت برندها، اطلاعات تماس و دامنه‌ها را با هم ادغام نکن.

| خوشه‌ی نیاز جست‌وجو | صفحه‌ی اصلی پیشنهادی | نکته |
|---|---|---|
| ماشین کوبنده شهربازی، ماشین برقی کوبنده، استعلام قیمت | /products و صفحه‌ی مستقل هر مدل | هر محصول عنوان و محتوای ویژه‌ی خودش را داشته باشد |

| طراحی و اجرای پیست ماشین کوبنده | /services یا صفحه‌ی خدمات تخصصی موجود | از /portfolio برای اثبات پروژه استفاده شود |
| پیست ماشین کوبنده بدون آنتن سقفی | محتوای تخصصی یا نمونه‌کار موجود | مکانیزم یا ادعای فنی جدید نساز؛ فقط داده‌ی تأییدشده را بیاور |

| شواهد اجرای پروژه | /portfolio و جزئیات هر پروژه | شهر، محدوده‌ی کار و نتیجه فقط با داده‌ی موجود |

## ۵. الزامات فنی

### ۵.۱. یکپارچه‌سازی دامنه

- نشانی canonical اصلی فعلی را بررسی کن. اگر همچنان https://mohammadiig.ir است، همان را به‌عنوان میزبان نهایی نگه دار.
- HTTP و میزبان www را در لایه‌ی تحت کنترل repository یا hosting با 301/308 به HTTPS بدون www هدایت کن.
- تغییرمسیر باید مستقیم، بدون chain و برای همه‌ی مسیرها، queryهای مجاز و صفحه‌های محصول درست کار کند.
- اگر کنترل سرور، CDN یا DNS در مخزن نیست، ادعای اصلاح‌شدن نکن؛ در گزارش تنظیم دقیق لازم و محل اعمال آن را بنویس.
- URLهای داخلی، sitemap و canonicalها را به نسخه‌ی نهایی واحد هماهنگ کن.

### ۵.۲. metadata یکتا برای هر URL عمومی

برای هر URL قابل ایندکس، مقدارهای server-rendered و منحصربه‌فرد زیر را بررسی و اصلاح کن:

- عنوان صفحه‌ی کوتاه، طبیعی و توصیف‌گر همان صفحه.
- meta description ویژه‌ی همان صفحه و متناسب با قصد کاربر.
- canonical self-referencing به URL نهایی HTTPS بدون www.
- Open Graph title، description، URL و تصویر متناسب با صفحه‌ی مهم.
- robots metadata مطابق سیاست index/noindex همان صفحه.

نمونه‌های جهت‌دهنده، قابل تغییر با توجه به متن و داده‌ی واقعی:

- صفحه‌ی اصلی: تولید ماشین کوبنده شهربازی و اجرای پیست | گروه صنعتی محمدی
- کاتالوگ: ماشین کوبنده شهربازی؛ محصولات و مدل‌ها | گروه صنعتی محمدی
- محصول: نام واقعی مدل | مشخصات و استعلام قیمت | گروه صنعتی محمدی
- خدمات: طراحی، نصب و پشتیبانی تجهیزات شهربازی | گروه صنعتی محمدی
- نمونه‌کار: عنوان واقعی پروژه و شهر، در صورت ثبت‌شده بودن | گروه صنعتی محمدی
- قطعات: قطعات یدکی ماشین کوبنده | گروه صنعتی محمدی

این نمونه‌ها را با تکرار کلیدواژه و ادعای تأییدنشده پر نکن. برای /projects، /services و /spare-parts metadata جدا بنویس. عنوان یا توضیح را با کد مشترک عمومی روی تمام routeها نگذار.

### ۵.۳. رندر سمت سرور و حفظ UI

- منبع داده‌ی موجود محصولات و پروژه‌ها را در repository پیدا کن و روش دریافت آن را بفهم.
- نام محصول، محتوای توضیحی، تصویر اصلی، تیتر اصلی و metadata باید در HTML اولیه‌ی URL جزئیات حاضر باشند.
- صفحه‌های کاتالوگ و نمونه‌کار باید محتوای واقعی و لینک‌های HTML قابل کشف داشته باشند؛ محتوا نباید فقط بعد از اجرای client JavaScript ساخته شود.
- برای Next.js، از الگوهای رسمی موجود در نسخه‌ی نصب‌شده‌ی پروژه استفاده کن؛ metadata داینامیک را در مرحله‌ی server route تولید کن و مسیرها را در صورت امکان با داده‌ی معتبر pre-render کن.
- رفتار client، eventها، API فعلی، hydration و مؤلفه‌های loading باید حفظ شوند. از یک API/data source معتبر مشترک استفاده کن تا نسخه‌ی سرور و مرورگر اختلاف داده نسازند.
- اگر fetch سمت سرور به token یا راز نیاز دارد، هیچ credential را به client منتقل نکن. از endpoint عمومی و امن موجود استفاده کن؛ endpoint مدیریتی تازه یا دسترسی بیش از حد نساز.
- اگر داده‌ی صفحه از ابتدا در دسترس است، وضعیت loading را به شکل طبیعی resolve کن؛ ظاهر و component طراحی loading را تغییر نده.
- خطاهای fetch و fallbackهای فعلی را نشکن. از تغییرات caching که داده‌ی محصول یا قیمت را قدیمی یا بین کاربران مشترک می‌کند پرهیز کن.

### ۵.۴. Sitemap و robots

- sitemap.xml را از فهرست canonical URLهای عمومی و indexable تولید کن.
- مواردی که باید بررسی شوند: صفحه‌ی اصلی، کاتالوگ، سه صفحه‌ی محصول فعلی، نمونه‌کار و جزئیات نمونه‌کار، خدمات، قطعات، درباره‌ما، تماس و درخواست قیمت؛ indexability درخواست قیمت را بر اساس محتوای واقعی صفحه تعیین کن.
- صفحه‌های /auth، /account/profile، /admin، سبد خرید یا مسیرهای خصوصی/عملیاتی را به sitemap اضافه نکن.
- noindexها را از sitemap حذف کن و URLهای redirect، 404، duplicate و پارامترهای غیرضروری را وارد نکن.
- lastmod را فقط با تغییر واقعی محتوا به‌روزرسانی کن.
- robots.txt فعلی و محدودیت /admin را حفظ کن. مسیرهای قابل ایندکس را با disallow مسدود نکن.

### ۵.۵. داده‌ی ساختاریافته

- Organization و WebSite موجود را حفظ کن و از ایجاد چند entity تکراری یا متناقض پرهیز کن.
- Product را فقط در صفحه‌ی محصول و با اطلاعاتی اضافه کن که در صفحه برای کاربر قابل مشاهده و از منبع معتبر خوانده شده‌اند.
- برای قیمت توافقی، قیمت ساختگی نساز و Offer با قیمت صفر یا placeholder درج نکن.
- aggregateRating، review، warranty، availability، brand، dimensions یا rating خیالی نساز.
- BreadcrumbList فقط در صورتی اضافه شود که مسیر breadcrumb واقعی و قابل مشاهده/معنادار در صفحه وجود دارد یا با URL واقعی منطبق است.
- اگر اطلاعات تلفن، ایمیل، نشانی یا sameAs استفاده می‌شود، باید با اطلاعات تأییدشده‌ی موجود سایت هماهنگ باشد.
- JSON-LD باید JSON معتبر و بدون خطای schema باشد. داده‌ی ساختاریافته تضمین نمایش rich result نیست.

### ۵.۶. تصویر، heading و لینک‌های داخلی

- برای عکس‌های واقعی محصول و پروژه alt توصیفی و غیرتبلیغاتی اضافه کن؛ برای تصویر کاملاً تزئینی alt خالی را نگه دار.
- width، height، loading و priority تصویرها را فقط با اندازه‌گیری و هدف بهبود عملکرد تنظیم کن؛ به ظاهر، crop، ترتیب یا کیفیت بصری تصویر دست نزن.
- هر صفحه‌ی indexable یک H1 معنایی داشته باشد. تغییر تگ heading باید classها و ظاهر فعلی را دقیقاً حفظ کند.
- CTAها، anchorها و لینک‌های موجود به صفحه‌ی محصول، پروژه‌ی مرتبط و استعلام قابل crawl باشند. متن و جای دکمه‌ها را عوض نکن.

### ۵.۷. محتوای ناقص و ادعاهای نیازمند تأیید

- داده‌ی محصولی که در repository وجود ندارد را نساز. از مالک کسب‌وکار یک فهرست موارد ناقص در گزارش نهایی ارائه بده.
- اختلاف «بیش از چهل سال» و «آغاز مسیر در ۱۳۸۱» را خودسرانه حل یا بازنویسی نکن. درخواست تأیید داده را در گزارش بیاور.
- محتوای visible را فقط با داده‌های منتشرشده و تأییدپذیر بهبود بده؛ layout جدید یا بخش تصویری تازه نساز.
- طرح تولید مقالات آینده را می‌توان در گزارش پیشنهاد داد؛ مقاله‌ی فنی با spec حدسی به سایت اضافه نکن.

## ۶. اولویت اجرای کار

### P0 — پیش از تولید محتوای زیاد

1. یکسان‌سازی HTTPS و میزبان canonical؛ اگر تنظیم بیرونی لازم است، مستندکردن آن.
2. metadata، canonical و HTML اولیه‌ی صفحه‌ی هر محصول.
3. جلوگیری از عنوان/توضیحات عمومی مشترک روی صفحه‌های محصول و خدمات.

### P1 — مرحله‌ی بعد

4. رندرشدن محتوا و لینک‌های کلیدی در HTML اولیه، با حفظ loaderها و منطق client.
5. تولید sitemap کامل و همسو با indexability و canonical.
6. metadata مستقل برای /projects، /services و /spare-parts.

### P2 — تکمیل و کیفیت

7. OG تصویرمحور، altهای معنادار، یک H1 معنایی برای هر صفحه.
8. Product و BreadcrumbList فقط برای داده‌ی معتبر و مناسب.
9. ثبت کمبودهای محتوایی و مغایرت ادعای سابقه برای تأیید مالک.

## ۷. معیارهای پذیرش

کار زمانی کامل محسوب می‌شود که:

- همه‌ی variantهای دامنه در محیط محلی/preview به میزبان نهایی redirect شوند یا مورد خارج از کنترل repository صریح گزارش شود.
- تمام URLهای indexable عنوان، توضیح و canonical یکتای صحیح داشته باشند.
- برای صفحه‌ی محصول، HTML اولیه شامل H1، نام، توضیح واقعی، تصویر و metadata اختصاصی باشد.
- محصول‌ها و نمونه‌کارهای عمومی با لینک HTML در کد قابل کشف باشند.
- sitemap فقط URLهای نهایی، canonical، عمومی و indexable را دربرگیرد؛ صفحه‌های جاافتاده اضافه و صفحه‌های خصوصی حذف شده باشند.
- JSON-LD معتبر باشد و هیچ قیمت، امتیاز، مشخصه یا ادعای ساختگی نداشته باشد.
- screenshot یا بررسی دیداری قبل/بعد برای صفحه‌های اصلی، کاتالوگ، محصول، نمونه‌کار و صفحه‌ی تماس نشان دهد طراحی، حالت‌های loading، انیمیشن و responsive behavior حفظ شده‌اند.
- مسیرهای اصلی سایت، فرم‌ها، APIها، سبد خرید و auth بدون regression کار کنند.
- build و بررسی‌های از قبل موجود پروژه موفق باشند. هیچ test suite جدیدی صرفاً برای این تغییر اضافه نشود مگر الزام فنی مستند وجود داشته باشد.
- Codex سایت production را deploy، push یا منتشر نکند.

## ۸. گزارش نهایی مورد انتظار از Codex

در پایان، Codex باید این موارد را گزارش کند:

1. فایل‌های تغییرکرده و دلیل هر دسته تغییر.
2. routeهایی که قبل و بعد از کار برای metadata، canonical، sitemap و HTML اولیه بررسی شده‌اند.
3. نتیجه‌ی build و بررسی‌های موجود پروژه.
4. نتیجه‌ی مقایسه‌ی بصری و رفتار loaderها، یا محدودیت ابزار برای بررسی آن.
5. هر موردی که به تنظیم CDN/hosting یا تصمیم مالک نیاز دارد.
6. مشخصات محصول و سابقه‌ای که برای تکمیل نیاز به تأیید مالک دارند.
7. مواردی که در این مرحله عمداً تغییر نکرده‌اند تا منطق یا UI آسیب نبیند.
